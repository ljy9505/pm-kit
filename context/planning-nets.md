# 기획 그물 — 파이프라인 단계별로 꽂는 점검 장치

> mattpocock/skills 파이프라인은 **엔지니어링 도구**라 기획자의 그물(엣지케이스·권한·반출·운영 축)이 없다.
> 이 파일은 그 빈자리를 채운다. `CLAUDE.md`의 파이프라인 지도에서 단계마다 이 파일의 해당 절을 가리킨다.
> 회사별 값(역할·상태·정책·DS)은 여기 쓰지 않는다 → `domain-context.md`.

---

## §1 grill 단계 — `/grill-with-docs`에 얹는 질문

`/grill-with-docs`가 질문을 던질 때 아래를 질문 목록에 반드시 섞는다. 상세는 `planning-kickoff.md`.

- **발산·문제정의 먼저**: "이 기능이 왜 필요한가 / 진짜 문제는 무엇인가 / 다른 방법은 없나". 막히면 `opportunity-solution-tree`·`jobs-to-be-done`·`problem-framing-canvas`·`lean-ux-canvas`.
- **전제 점검**: 기획이 딛고 있는 전제 3~5개에 각각 **확인됨/추정/모름**. '추정·모름'은 오픈 이슈로, 그 위에 세운 기능엔 표시. 근거는 링크만 말고 출처명·제목·발행일까지.
- **어드민 범위**부터 확정(ⓐ서비스+어드민 / ⓑ서비스만 / ⓒ어드민만).
- **아직 정의 안 된 것** 5~7개 역질문. 추측으로 채우지 않는다.
- **엣지케이스 6분류**(§6)를 시나리오 질문으로 돌린다 — `domain-modeling`의 "edge-case 시나리오로 용어 검증"과 같은 자리다.
- **용어 결정은 그 자리에서 용어집에** — 제품 고유 용어·상태값은 제품 레포 용어집, 회사 공통 역할·정책은 `domain-context.md`. 같은 용어를 두 곳에 쓰지 않는다(한쪽이 반드시 낡는다).
  - 용어집 파일은 **회사 표준에 용어 문서가 있으면 그것**(예: `docs/glossary/app-terms.md`), 없을 때만 루트 `GLOSSARY.md`. `/setup-matt-pocock-skills` 때 `docs/agents/domain.md`에 그 경로를 적는다.

## §2 문서 작성 단계 — 회사 표준 문서(정본)

순서: **정책서 → 기능 정의서 → 화면 설계서** (어드민/관리 세트 먼저, 그다음 사용자용). 양식·경로·ID는 회사 표준(`doc-standard.md` 또는 대상 레포 `docs/conventions.md`)이 정본 — 이 엔진의 골격으로 문서를 새로 깔지 않는다.

- 표준에 **없는 그물**(전제 점검·운영 축·지표 이벤트·예측/Eval)은 버리지 말고 **표준 문서를 건드리지 않는 자리**에 얹는다 — 기존 섹션에 항목 추가하거나, 표준이 쓰지 않는 파일명으로 신규 생성.
- **문서 소유 경계를 침범하지 않는다** — 화면 설계서(레이아웃)가 디자이너 소유인 조직이면 기획자 산출물은 그 앞 단계까지.
- 모든 예외는 **`조건 → 시스템 동작 → 화면에 보이는 것`** 3단으로. 상태 그물은 `ux-checklist.md`(로딩·빈상태·**가역성(Undo vs 모달)**·폼·접근성·**주된 행동·패턴 일관성**)를 훑어 빠진 화면 상태를 채운다.
- **파괴적 액션은 가역성부터 판정한다** — 되돌릴 수 있으면 Undo 토스트, 없으면 확인 모달, 비가역+대량·과금이면 둘 다. "확인 모달"을 반사적으로 붙이지 않는다(모달은 무조건 확인 누르기로 훈련시켜 정작 위험할 때 안 먹는다). Undo를 고르면 soft delete·유효시간·원복 이력이 스키마 선행조건이라 **개발 시작 후엔 못 넣는다** → 기능 정의서 "상태 전이"에 원복 전이를 같이 적는다.
- 리소스마다 **권한 × CRUD 매트릭스** — `—`(불가) 칸엔 "어떻게 막는지"까지. 빈칸 = 구멍.
  **조회(R)를 적었으면 반출(다운로드·인쇄·복사·API)도 같은 줄에** — 허용 역할 / 반출 범위(화면 필터가 파일에 반영되나) / 화면 마스킹 항목이 파일엔 원본으로 나가나 / 다운로드 이력. 조회만 적고 반출을 안 적는 것이 가장 흔한 누락이고, 사고 나면 개인정보 유출이다.
- **운영 축 5칸(측정·알림·소급·운영CS·법)** — 기능마다 훑는다(동작이 맞아도 출시 후 사고는 이 5칸에서 난다). 측정=성공 지표 이벤트 + **UX 품질 지표**(단계별 이탈 지점·재시도/중복 제출률·동일 CS 반복 — 기능 지표만 세면 화면 문제가 "기능 실패"로 오독된다) / 알림=발송조건·대상·수신거부·중복야간 / 소급=배포 시점 기존 데이터·진행 중 건 / 운영CS=사람이 손으로 처리하는 케이스 / 법=신규 개인정보 수집·동의·보유파기·고지.
  - **회사 문서 표준이 있으면 5칸 표를 덧붙이지 않는다.** 표준의 기존 칸으로 흘려보낸다 — 측정→지표·이벤트 문서 + 이벤트 ID 한 줄 / 알림→"규칙·정책"(알림 자체가 기능이면 기능 한 행으로 승격) / 소급→"상태 전이"·규칙 / 운영CS→**어드민 기능으로 승격** / 법→서비스 정의서 제약, 동의 UI는 화면 설계서.
  - 흘려보낸 뒤 각 기능 하단에 **운영 점검 한 줄**만 — `측정 EV-012 / 알림 없음 / 소급 신규만 / CS AF-024 / 법 없음`. 이 한 줄이 없으면 "검토했는데 해당 없음"과 "아예 안 봤음"이 6개월 뒤 구분되지 않는다.
  - 표준이 없는 프로젝트에서만 5칸을 표로 유지한다.
- 문서는 **"무엇인가"만** — 구현 방식·API·DB·"어느 파일 어떻게"는 안 적는다(그건 `/to-spec`·`/to-tickets` 이후 개발 몫). 정책(무엇을 허용/금지)은 기획 소관이라 남긴다.

## §3 프로토타입 단계 — `/prototype`에 얹는 규칙

`/prototype`은 기능 정의서 작성 **중에** 함께 돌린다(넘긴 뒤가 아니라 동시). 정책이 바뀌면 프로토타입도 같이 고친다.

**실제 코드 기반 — 예외 없음.** 단독 HTML·빈 캔버스 목업으로 화면을 그리지 않는다.
- **기획 레포에 코드가 없으면** `.claude/context/code-repos.md`에 적힌 코드 레포에서 만든다(없으면 PM에게 코드 레포 경로를 묻고 그 파일을 만든다). 코드 레포의 프로토타입 브랜치는 **로컬 전용 — push·PR 금지**. 팀 공유용 프로토타입이 따로 정해진 레포면(예: HTML) 그것은 팀 규칙대로 두고, 로컬에서 정한 방향을 거기 반영한다.
- **코드에 아예 접근할 수 없으면**(코드 레포 권한 없음·아직 코드 없는 신규 제품) PM에게 확인받은 뒤에만 단독 HTML 프로토타입으로 대신한다. 이때 회사 DS 문서·기존 제품 화면 캡처를 기준으로 삼고, 화면 하단에 "실제 코드가 아님 — 데이터·권한·화면 틀은 추정"을 표시한다. `impeccable`로 다듬는 건 같다.
- **먼저 읽는다**: 만들기 전에 대상 제품 레포의 해당 화면 라우트·쓰는 컴포넌트·데이터 형태(API 응답·타입)를 읽고, 무엇을 읽었는지 한 줄로 밝힌다.
- **기존 화면 안에 띄운다**: 기존 페이지에 `?variant=`로 변형을 띄운다(`/prototype` UI.md의 A형). 새 기능도 들어갈 기존 페이지 안에 붙인다. 정말 들어갈 페이지가 없을 때만 그 레포 라우팅 규칙대로 `prototype` 이름이 붙은 새 라우트를 만든다.
- **새 기능도 현재 코드 기준**: 지금 있는 데이터·타입·권한 판정을 그대로 쓴다. 아직 없는 데이터는 가짜 값을 하드코딩하되 `PROTOTYPE STUB` 표시를 하고, 화면 아래에 "이 화면이 새로 요구하는 데이터" 목록을 남긴다. 이 목록이 기능 정의서와 `/to-spec`의 입력이다.
- **로직 질문도 실제 코드**: 상태·흐름을 검증하는 프로토타입(LOGIC.md)도 레포에 있는 상태 정의·도메인 모듈을 가져다 쓴다. 가짜 상태 모델을 새로 만들지 않는다.
- **디자인시스템을 먹인다**: 화면은 `domain-context.md`에 적힌 회사 DS 패키지의 실제 컴포넌트·토큰만 쓴다. 색·간격·글꼴 값을 직접 적지 않는다. DS에 없는 컴포넌트가 필요하면 ⚠️ 라벨을 달고 만들기 전에 PM에게 묻는다.
- **실제 화면 틀 안에서**: 그 레포의 실제 헤더·사이드바(GNB/LNB)와 실제 데이터 밀도 안에서 본다. 빈 라우트에서는 모든 변형이 괜찮아 보인다.
- **본 코드와 분리**: 프로토타입은 별도 브랜치에 둔다. 이긴 안은 본 코드로 다시 제대로 짠다(프로토타입 코드를 그대로 배포하지 않는다). 커밋은 PM이 한다.

- **변형 2~3개는 아래 «UX 2~3안» 규칙으로 고른다** — 각 안 = 컴포넌트 / 인터랙션 / 편의성 트레이드오프 / 엣지케이스(조건→동작→화면), 출처 라벨 필수:
  - ✅ **DS 있음**: 표준 패턴 + 회사 디자인시스템에 실제 존재 → 안심 채택
  - ⚠️ **표준이나 커스텀 필요**: 관례지만 DS엔 없음(바텀시트·스켈레톤 등) → PM이 판단
  - 🚫 **안 흔함**: 실험적/니치 → 제안 안 함
  - 안 흔한 걸 "표준"인 척 포장 금지. 애매하면 확신 없다고 먼저 밝힌다. 대한민국 IT 표준 관례 패턴(모달·토스트·드롭다운)이면 익숙함=사용성이므로 DS 밖이어도 제안 OK.
- **화면 한 장마다 «모드»(설득·처리·읽기·체험)를 한 줄로 못 박는다** — `prototype-craft.md`. 똑같은 카드 3장·섹션마다 붙는 작은 라벨·1건인데 3열 그리드·줄표 같은 AI 반사 구성을 미리 막는다.
- **데이터 0건·1~2건·꽉 찬 상태를 같이 그린다** (`prototype-craft.md` §3). 0건만 잡고 1건을 안 잡는 것이 가장 흔한 누락.
- **프로토타입 크롬**: 폼만 두지 말고 GNB/LNB로 감싸 맥락을 보이게.
- DS 밖 컴포넌트·모션·3D를 넣기 전엔 `prototype-craft.md` §5 — 시안에 넣는 순간 "이대로 만들어 달라"가 되므로 **개발 비용을 먼저 묻는다.**
- **다듬기는 코드에서 한다(Figma 없이).** 이긴 안을 같은 브랜치에서 `impeccable`(critique → polish)로 다듬고, 모바일·태블릿·데스크톱 세 화면 폭의 스크린샷을 찍어 PM에게 보여준다. Figma는 선택 — 무료 플랜은 MCP 호출 한도가 월 몇 회 수준이라 다듬는 도구로 못 쓴다.
- 받자마자 **PM이 직접** `prototype-craft.md` §4 사전점검(5분)을 돈다.

## §4 넘기기 직전 — `/to-spec` 앞

- **`planning-reviewer` 통과가 `/to-spec`의 입장권** — 권한 CRUD 빈칸 0 + 운영 축 미정의 0.
- **`/to-spec`은 회사 표준 문서를 요약하는 전달용 이슈다.** 정본은 표준 문서. 스펙 본문에 정책을 새로 쓰지 말고 정본 문서 경로와 기능 ID(AF-/SF-)를 건다. 스펙과 정본이 어긋나면 정본이 이긴다.
- **출시·롤아웃 계획**: 롤아웃 방식(전체/선공개/기간한정) · **끌 수 있는 스위치**(코드 롤백 말고 기획자가 끄는 것) · 중단 기준(숫자) · 구버전/기존 사용자 처리 · 공지·CS 시점. 되돌리는 법이 "코드 롤백"뿐이면 계획이 없는 것. → 스펙의 "Further Notes"에 넣는다.
- **예측 일지 + Eval 세트** — `prediction-eval.md`.
  - 예측 2~3개(판정 가능한 문장) + 근거 + **확인 시점 날짜**. 그 날짜에 열어보고 `틀린 방향`을 한 줄. 판단을 글자로 박아두지 않으면 사후확신 편향으로 학습이 0이 된다.
  - **출력이 매번 달라지는 기능**(AI/LLM·추천·검색·랭킹·자동분류)이면 Eval 세트: 케이스 30개 이상 + 통과선(정확 %) + **절대 금지(P0) 0건**. P0엔 되돌릴 수 없는 동작(발송·결제·삭제·개인정보 노출)을 넣는다. 케이스 축 = 6분류 + 모호성·표기변형·범위밖·드리프트. 케이스 작성은 개발자·모델에게 넘기지 않는다.
  - 모델·프롬프트·참조데이터가 바뀌면 같은 세트 재실행하고 버전으로 남긴다.

## §5 구현 후 — `/implement`·`code-review` 뒤

- **`code-review`의 Spec 축은 "코드가 스펙과 맞나"를 글로 대조한다. 화면을 눌러보지 않는다.** 그래서 기획자 QA를 대체하지 못한다.
- 개발 완료 후 **`qa-engineer`**(실제 브라우저)를 돈다 — 기획서를 기대값으로 6분류 + **반출** 축, 그리고 **화면에 있는데 문서에 없는 기능**(역방향 갭 스캔)을 따로 모아 PM에게 되돌린다.
- 배포 전·회차 마감에 `intended-vs-implemented`로 정본↔코드 일치를 훑는다(설치돼 있으면).
- QA 버그는 회사 표준 트래커로(domain-context 참조).

## §6 엣지케이스 6분류 (도메인 불문 고정 — 항상 훑는다)

**권한 · 상태 · 입력 · 시점 · 연동 · 데이터**
(권한 우회 / 허용 안 된 상태 전이 / 빈값·최대·중복·경계값 / 이미 처리·만료·취소 후 재요청 / 외부 실패·부분성공 / 삭제 시 이력·되돌리기)

시스템·기술 예외도 항상 포함: 네트워크 끊김·타임아웃, 초기진입 유저 Empty State, 중복클릭·다중요청, 세션만료 시 데이터 보존, 외부툴/웹훅 연동오류, 로그적재 실패·지연.
> 각 예외는 **[유저에게 미치는 영향] + [UX/시스템 해결방안]**(에러 노출/버튼 비활성화/기본값 대체 등)을 함께 쓴다.

## §7 의도 기반 아이데이션 (대화 습관 — 문서엔 안 씀)

기능·버튼·UI를 배치할 때, 결과(what)를 정하기 전에 **의도(이 요소가 사용자에게 주는 가치)를 대화로 짚는다.** PM이 결정을 잘 내리기 위한 사고 재료라 문서·프로토타입엔 안 쓴다.

- **의도 되짚기**: "이 요소 = 어떤 사용자 가치? 제 읽기론 X인데 맞나요?"
- **발산**: "의도가 Y였다면 배치가 이렇게 바뀝니다."
- **'빼면 죽는 것' 게이지**(확신 안 설 때만): "이거 빼면 무슨 가치가 새나?"

방어선: PM이 반응할 제안으로 낸다(판단·채택은 PM). 관례 명확한 배치(저장=우하단 등)엔 발동 안 함. 의도가 갈리고 그게 사용자 가치를 바꾸는 분기에서만.
