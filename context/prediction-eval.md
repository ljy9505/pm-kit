# 예측 일지 · Eval 세트 (넘기기 직전 엔진)

> 기획을 **넘기기 직전**에 채우고, **정한 날짜에 열어보는** 파일.
> 이 엔진은 회사가 바뀌어도 그대로 쓴다. 회사별 값은 `domain-context.md`에만 둔다.

## 왜 이 단계가 있나 (ABC)

기획은 피드백 루프가 끊긴 직무다. 결과는 3~6개월 뒤에 나오는데, 그때쯤이면 **내가 무엇을 근거로 그렇게 판단했는지 기억이 이미 왜곡돼 있다**(사후확신 편향: "그럴 줄 알았지"). 그래서 10년을 해도 1년치 경험이 열 번 반복되기 쉽다.

해결은 하나뿐이다 — **판단을 글자로 박아두고, 나중에 채점한다.**

- **예측 일지** = 내 *판단*이 맞았는지 채점 → 모든 기획에 적용
- **Eval 세트** = 내가 만든 *기능*이 맞았는지 채점 → 출력이 매번 달라지는 기능에만 적용

둘은 같은 메커니즘이라 한 파일에서 관리한다. 산출물은 `docs/04-prediction-eval.md`.

---

## Part A — 예측 일지 (모든 기획 공통, 필수)

기획서를 프로토타입/개발로 넘기기 **직전**에 3줄 적는다. 5분이면 된다.

```markdown
### [2026-08-12] F-006 트랙 제출  ·  확인 시점: 2026-09-15

**예측** (판정 가능한 문장으로, 2~3개)
1. 참가팀의 60% 이상이 마감 3일 전에 제출한다
2. CS 문의 1위는 "제출 후 트랙 변경 가능한가요"다
3. 어드민 반려 사유 중 '제출물 형식 오류'가 40% 이상이다

**근거**
- 유사 대회 A 제출 로그 (2026-03, 사내 BigQuery)
- 어드민 문의 채널 최근 3개월 로그

**가장 불안한 전제** — 참가팀이 트랙 정의를 제출 전에 읽는다 (모름)
```

확인 시점이 되면 같은 블록 아래에 이어 쓴다:

```markdown
**[확인 2026-09-15]**
- 실제: ① 78% (맞음) ② 1위는 "팀원 추가"였음 (틀림) ③ 22% (틀림)
- **내가 틀린 방향**: 사용자가 문서를 읽는다고 과대평가함. 2건 연속 같은 패턴.
```

### 규칙

| 규칙 | 이유 |
|---|---|
| 예측은 **숫자 또는 O/X로 판정 가능한 문장**으로 | "잘 될 것이다"는 채점이 안 되므로 학습이 0 |
| 확인 시점을 **날짜로** 못 박는다 | 날짜가 없으면 영원히 안 열어본다 |
| **틀린 예측을 지우지 않는다** | 지우는 순간 이 파일의 유일한 가치가 사라진다 |
| `틀린 방향`을 한 줄로 적는다 | 20~30건 쌓이면 **내 판단의 계통 오차**가 보인다 (이게 진짜 성장 지점) |
| 3개 이하로 쓴다 | 10개 적으면 다음부터 안 쓴다 |

> **성장 신호**: 개별 예측의 적중률이 아니라, `틀린 방향`에 같은 문장이 반복되는지를 본다.
> "사용자의 학습 의지를 과대평가" 같은 패턴이 잡히면 그 편향을 다음 기획에서 미리 깎을 수 있다.

## Part B — Eval 세트 (출력이 매번 달라지는 기능만)

### 언제 발동하나 (아래 중 하나라도 해당되면 필수)

- AI·LLM이 관여하는 기능 (생성·요약·분류·번역·STT·챗)
- **추천·검색·랭킹** (같은 입력에 결과 순서가 바뀔 수 있음)
- 자동 매칭·자동 분류·이상탐지 (규칙이 아니라 점수로 판정)

> 결정론적 기능(버튼 누르면 항상 같은 결과)은 Part B **생략**. 기존 예외 표(조건→동작→화면)로 충분하다.

### 왜 기존 예외 표로는 안 되나 (ABC)

기존 기획서의 예외 표는 **맞다/틀리다가 명확한 기능**을 전제로 한다. 확률적 기능은 세 가지가 다르다:

| | 결정론적 기능 | 확률적 기능 |
|---|---|---|
| 기대 동작 | 하나로 확정 | **허용 범위** + **절대 금지**로 나뉨 |
| 통과 판정 | 케이스 하나하나 통과 | **N개 중 몇 %** |
| 회귀 | 코드 안 건드리면 안 깨짐 | **모델·프롬프트·데이터가 바뀌면 조용히 깨짐** |

그래서 "이 기능 좋아졌나요?"에 아무도 답을 못 하는 상태가 기본값이 된다. Eval 세트는 그 질문을 **결정 가능한 질문**으로 바꾼다.

### 케이스 세트 만드는 법

**엣지케이스 6분류(권한·상태·입력·시점·연동·데이터)를 그대로 쓰고**, 확률적 기능 전용 축 4개를 더한다:

| 축 | 무엇을 넣나 | 예 (음성 → 자막) |
|---|---|---|
| **모호성** | 입력이 여러 해석이 가능한 경우 | 동음이의어, 배경 소음 중 발화 |
| **표기 변형** | 같은 뜻 다른 표기 | "오만원 / 5만 / 50000", "리액트 / React" |
| **범위 밖** | 이 기능이 **답하면 안 되는** 입력 (거부가 정답) | 강의 외 잡담 구간, 개인정보 발화 |
| **드리프트** | 길이·누적에 따른 품질 저하 | 90분 강의 후반부 정확도 |

케이스 수: **최소 30개, 권장 50개.** 10개짜리는 1건 실패가 10%p로 튀어서 개선 여부를 판단할 수 없다.

> 함정: 모델이 잘하는 케이스로 채우면 통과율만 예쁜 자기충족 세트가 된다.
> **실패할 것 같은 케이스를 절반 이상** 넣는다. 통과율이 처음부터 95%면 세트가 쉬운 것이다.

### 케이스 표 양식

```markdown
### F-0XX <기능명> Eval 세트  ·  v1  ·  2026-08-12

**통과선** (PM이 정하고 근거를 적는다)
- 정확: 90% 이상 — 근거: 10건 중 1건 오류까지는 사용자가 직접 수정 가능
- **절대 금지(P0): 0건** — 1건이라도 나오면 출시 불가
- 측정: 아래 세트 50건을 1회 실행, 사람이 판정

| # | 축 | 입력 | 허용 (통과) | 절대 금지 (P0) |
|---|---|---|---|---|
| 1 | 모호성 | 수취인 "김민수" (동명이인 3명) | 3명 노출 + 최근 이체순 | 임의로 1명 선택해 진행 |
| 2 | 표기변형 | "오만원" | 50,000원 | 5,000원 / 500,000원 |
| 3 | 범위밖 | "내 잔액 얼마야" | 이체 기능 아님을 안내 | 임의 금액으로 이체 화면 진입 |
| 4 | 시점 | 이미 취소된 이체 "다시 보내줘" | 원거래 취소됨 안내 | 취소 건을 그대로 재실행 |
```

**절대 금지(P0)가 이 표의 핵심이다.** 확률적 기능을 평균 점수로만 통과시키면, 발생 확률 1%짜리 치명적 오동작이 "정확도 99%"에 숨는다. 금전·개인정보·되돌릴 수 없는 동작(발송·결제·삭제)은 반드시 P0 열에 들어간다.

### 회귀 — 언제 다시 돌리나

아래 중 하나라도 바뀌면 **같은 세트를 다시 실행**하고 결과를 버전으로 남긴다.

- 모델 교체·버전 업 / 프롬프트·툴 정의 수정 / 참조 데이터·인덱스 변경 / 정책 변경

```markdown
| 버전 | 날짜 | 무엇이 바뀜 | 정확 | P0 | 판정 |
|---|---|---|---|---|---|
| v1 | 2026-08-12 | 최초 | 82% | 2건 | ❌ 출시 불가 |
| v2 | 2026-08-20 | 도메인 용어 사전 추가 | 93% | 0건 | ✅ |
```

이 표 한 장이 있으면 "STT 도입할까요?"라는 감(感) 논의가 **"몇 %에서 도입할지"라는 결정 가능한 질문**으로 바뀐다. 이게 Eval의 실제 효용이다.

## 이 단계에서 하지 말 것

- 판정 불가한 예측 적기 ("반응이 좋을 것이다") → 채점 안 되면 안 적은 것과 같다
- 확인 시점을 "나중에"로 두기 → 안 열어본다
- 틀린 예측 삭제·수정하기 → 이 파일의 유일한 가치를 없애는 행위
- **Eval 케이스를 개발자·모델에게 맡기기** → 무엇이 사고인지는 도메인을 아는 PM만 안다. 여기가 PM이 대체 불가한 지점이다
- 통과선 없이 세트만 만들기 → "좋아 보인다"로 회귀
- 평균 정확도만 보고 P0 열을 비우기 → 1%의 치명적 오동작이 숨는다
- 프롬프트·모델 바꾸고 재실행 없이 넘기기 → 조용히 깨진 채로 배포된다
- 예측·Eval을 통과 조건이 아니라 **참고 자료**로 두기 → 안 쓰게 된다
