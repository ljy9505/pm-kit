# 기획 작성 킥오프 — 초안 쓰기 전에 이걸 먼저 (엣지케이스 강제 발굴)

> 기획서 초안을 쓰기 **전에** `.claude/context/domain-context.md`와 함께 이 파일을 참조한다.
> 파이프라인 1단계(`/grill-with-docs`, `/pm-flow` 1단계)에서 질문 목록으로 쓴다. 여기서 정한 용어는 바로 `GLOSSARY.md`로.
> 목적: 빈 문서에서 바로 쓰지 말고, 빈틈을 먼저 드러낸 뒤 쓰기 위함.
> 프로젝트별로 커스터마이즈하려면 이 파일을 `.claude/context/planning-kickoff.md`로 복사해 수정한다.

## STEP 0. 전제부터 꺼내기 (질문의 각도 점검)

빈틈을 묻기 전에, 이 기획이 딛고 있는 전제부터 적는다. 각도가 틀리면 그 아래 문서는 정확하게 틀린 채로 완성된다.

```
초안을 쓰기 전에, 이 기획이 깔고 있는 전제를 3~5개 뽑고 각각에
[확인됨 / 추정 / 모름]을 붙여라. 그다음 이 접근에서 내가 안 보고 있는 관점과,
최근 변화 중 이 전제를 흔드는 것이 있는지 짚어라.
근거를 댈 때는 링크가 아니라 출처명·제목·발행일을 적어라.

그리고 각 문장이 [관찰 / 해석 / 가정 / 결정] 중 무엇인지 표시하라.
해석을 관찰처럼 쓰지 마라.
```

- '추정·모름'은 회사 표준이 정한 **오픈 이슈 자리**(없으면 오픈 이슈 목록)에 남기고, 그 위에 세운 기능에 표시한다. 의사결정 로그를 Notion 등 다른 도구에 두는 조직이면 `decisions.md`를 새로 만들지 않는다.
- 비교("무엇이 무엇과 다른가")보다 변화("무엇이 왜 뒤집히고 있는가")를 먼저 본다.

**네 분류를 섞어 쓰지 않는다** — 실무에서 제일 사고 나는 건 *해석이 관찰인 척* 본문에 들어가는 것이다. "사용자는 ~를 원한다"가 조사 결과인지 내 추측인지 문장만 봐선 구분되지 않고, 그 위에 기능이 세워진다.

| 분류 | 뜻 | 예 |
|---|---|---|
| **관찰** | 근거에서 직접 본 것 | "제출물 미열람 CS가 지난달 12건" |
| **해석** | 관찰을 묶어 내린 판단 = **가설** | "주최사가 제출물 위치를 못 찾는 것 같다" |
| **가정** | 검증 안 하고 참으로 둔 것 | "주최사는 대부분 데스크톱으로 본다" |
| **결정** | 사실 여부와 무관한 선택 | "이번엔 알림을 붙이지 않는다" |


## STEP 0-R. 전략 레드팀 (전제를 꺼낸 뒤 · 초안 전 · 2026-09-07 신설)

STEP 0이 전제를 **꺼내는** 단계라면, 여기는 그 전제를 **흔드는** 단계다. planning-reviewer는 문서가 생긴 뒤 문서를 검토하므로 「이 기능이 왜 필요한가」 층의 가정은 검토 없이 지나간다 — 그 빈 자리. gstack `/office-hours`의 강제 질문과 pm-skills `strategy-red-team`(가정을 적대적으로 흔들어 위험 순위를 매김)을 우리 흐름에 맞춰 옮겼다.

```
아래 여섯을 한 번에 답하라. 답할 수 없으면 「모름」이라 적고 그것을 오픈 이슈로.
1. 진짜 고통은 무엇인가 — 누가, 언제, 지금은 어떻게 버티나(대체 수단). 「불편할 것 같다」는 답이 아니다.
2. 가장 작은 시작점은 무엇인가 — 이 기획의 1/3만 만들면 무엇이 검증되나. 그것만으로 안 되는 이유가 있나.
3. 안 만들면 무슨 일이 생기나 — 6개월 뒤 무엇을 잃나. 아무것도 안 잃으면 왜 지금인가.
4. 가장 불안한 전제는 무엇이고, 그것이 틀리면 무엇이 무너지나 — STEP 0의 [추정·모름] 중 하나를 고른다.
5. 이 기능이 있는 서비스와 없는 서비스(벤치마크 셋)는 각각 왜 그렇게 했나 — 없는 쪽의 이유를 먼저 적는다.
6. 죽이는 조건 — 출시 뒤 어떤 숫자·문의가 나오면 이 기능을 끄나. 숫자로.
```

- 답 여섯을 **위험 순위**로 정렬한다(틀렸을 때 잃는 것 × 틀릴 확률). 1위는 서비스 정의서 「전제·근거」와 예측 일지(`prediction-eval.md`)의 「가장 불안한 전제」로 그대로 간다.
- **기획자 혼자 답하지 않는다** — 디자인·개발 세션이 살아 있으면 그쪽에 같은 여섯을 던져 반박을 받는다.
- 여기서 「가장 작은 시작점」이 원안보다 작게 나오면 **범위를 줄이고** STEP 1로 간다. 줄인 이유를 오픈 이슈 자리에 한 줄.
## STEP 0++. 멈출 조건 (조사 시작 전에)

조사를 **시작하기 전에** 끝낼 선을 적는다. AI는 무한히 조사하고 무한히 문서를 뽑지만, 내가 읽고 책임질 수 있는 양은 그대로다. 검토 못 한 문서는 자산이 아니라 부채다 — 개발이 그걸 진짜로 구현하기 때문이다.

- 이 질문에 답하는 데 **필요한 최소 근거**는 무엇인가
- 같은 결론이 **몇 개 출처**에서 나오면 그만 보는가
- 조사를 **언제** 끝내는가 (시간 또는 건수)
- 이 단계의 산출물은 **몇 장**인가

> 「출처를 더 찾는 능력만큼 그만 찾을 조건도 필요하다.」 — 조사량이 아니라 결정의 선명함이 산출물이다.

## STEP 0+++. 판정 기준은 결과보다 먼저 (해당하면)

성공/실패를 가르는 **숫자·기준·임계값은 데이터를 보기 전에** 적는다. 보고 나서 정하면 그건 기준이 아니라 사후 정당화다.

- 성공 지표의 **통과선**을 지표 정의와 같은 시점에 적는다
- 롤아웃 **중단 기준(숫자)**을 출시 전에 적는다 (`docs/04-prediction-eval.md`)
- 심사·자격·승인처럼 여러 조건을 보는 로직은 **종합 점수보다 순차 게이트**를 먼저 검토한다 — 점수는 나쁜 항목을 좋은 항목이 덮어서 "왜 통과했는지"를 설명하지 못하고, 게이트는 **어디서 떨어졌는지가 남는다**

## STEP 0+. 어드민 범위 확정 (역질문보다 먼저)

초안·역질문 전에 어드민 포함 범위부터 못 박는다:
> "이 기획에 **어드민(관리자) 기능도 포함**할까요? — ⓐ 서비스+어드민 함께 / ⓑ 서비스만(어드민은 기존으로 충분) / ⓒ 어드민만"

왜: 서비스가 만드는 데이터는 결국 **어드민에서 조회·수정·삭제·상태변경**해야 한다. 서비스만 기획하면 "이 데이터 관리 화면이 없다"가 출시 후 터진다.
- ⓐ면 STEP 3의 권한 CRUD를 **서비스+어드민 짝**으로 채운다.
- ⓑ면 이 데이터가 **기존 어드민으로 관리 가능한지** 확인하고, 불가하면 갭을 오픈 이슈로 남긴다.

## STEP 1. 작성 전 역질문 (Claude가 나에게 되묻게 하기)

작성 지시에 이 문장을 붙인다:

```
초안을 쓰기 전에, 아래에서 '아직 정의되지 않은 것'을 5~7개 질문으로 먼저 되물어라.
내가 답한 뒤에야 초안을 작성한다. 추측으로 채우지 마라.
- 권한별 가능/불가능 액션 (각 역할이 못 하는 것)
- 허용되지 않는 상태 전이와 그때의 시스템 동작
- 실패 / 중복 / 동시성 처리
- 빈 상태 / 최대치 / 경계값
- 외부 연동 실패 시 처리
- 데이터 삭제 시 이력 보존·되돌리기
- 이 기능이 만드는/바꾸는 데이터를 어떤 어드민 권한이 CRUD 하는가
- 성공을 무엇으로 세는가 (이벤트가 심겨 있는가)
- 이 기능이 보내는 알림의 조건·대상·수신 거부
- 배포 시점의 기존 데이터와 진행 중인 건 처리
- 사람이 손으로 처리해야 하는 케이스
- 새로 수집하는 개인정보와 고지 필요 여부
- MO/TAB/WEB에서 각각 무엇이 보이는가 — 특정 해상도에서 빠지거나 달라지는 기능 (있으면 그게 정책)
```

## STEP 2. 초안 작성 규칙

- 문서 순서: **정책서 → 기능 정의서 → 화면 설계서** (어드민/관리 세트 먼저, 그다음 사용자용)
- 모든 예외는 **`조건 → 시스템 동작 → 화면에 보이는 것`** 3단으로 쓴다.
- 용어는 `domain-context.md` / glossary를 따른다. 임의 명명 금지.
- **기능마다 「약속하지 않는 것」을 쓴다** — 범위는 포함 목록이 아니라 제외 목록으로 정해진다. 이게 없으면 개발·디자인·영업이 각자 다른 걸 상상하고 "이것도 되는 줄 알았는데"로 터진다. (`doc-standard.md` §4)

## STEP 3. 권한 × CRUD 매트릭스 (반드시 채우고, 빈칸 = 구멍)

각 리소스마다 아래 표를 만든다. `-`(불가) 칸에는 **"어떻게 막는지"**까지 쓴다.

### 예시: 리소스 = "수강 신청"

| 역할 | Create(신청) | Read(조회) | Update(수정) | Delete(취소) |
|---|---|---|---|---|
| 매니저 | ✅ 대리신청 | ✅ 전체 | ✅ 상태변경 | ✅ (사유 기록) |
| 강사 | — (버튼 비노출) | ✅ 담당분만 | — | — |
| 수강생 | ✅ 본인 | ✅ 본인만 | — (마감 후 잠금) | ✅ 결제 전만, 이후 환불규정 |
| 게스트 | — (로그인 유도) | — | — | — |

> `—` 칸의 "어떻게 막는지"(버튼 비노출/잠금/리다이렉트)가 비면, 그게 권한 우회 엣지케이스다.

**어드민 포함(ⓐ)이면 어드민 역할도 이 표에 함께 넣는다.** 서비스가 만든 데이터를 어드민이 관리(수정·삭제·상태변경)하는 CRUD가 비면 관리 화면 누락이다.

## STEP 4. 넘기기 전 셀프 게이트

프로토타입/개발로 넘기기 전 아래를 스스로 확인 → 그다음 `planning-reviewer` 에이전트 실행:
- [ ] 조사 **시작 전에** 멈출 조건을 적었고, 그 선에서 멈췄다
- [ ] 성공 지표의 통과선·중단 기준을 **결과를 보기 전에** 적었다
- [ ] 기능마다 **「약속하지 않는 것」**이 있다
- [ ] 본문에서 관찰·해석·가정·결정이 구분된다 (해석이 관찰인 척하지 않는다)
- [ ] 모든 예외에 `조건 → 동작 → 화면`이 있다
- [ ] 리소스마다 권한 CRUD 매트릭스가 있고 빈칸이 없다
- [ ] 상태 전이표에 "허용 안 된 전이"가 명시돼 있다
- [ ] 외부 연동마다 "실패 시 처리"가 있다
- [ ] (어드민 포함 시) 서비스 데이터마다 그걸 관리하는 어드민 기능(CRUD)이 짝으로 있다
- [ ] 모르는 것을 "오픈 이슈"로 적어뒀다 (모른다는 걸 아는 것)
- [ ] 모든 성공 지표에 "세는 방법"이 붙어 있다
- [ ] 알림마다 발송 조건, 대상, 수신 거부가 있다
- [ ] 배포 시점의 기존 데이터·진행 중인 건 처리를 정했다
- [ ] 자동으로 안 되는 케이스를 처리할 어드민 기능이 있다
- [ ] 문제 생겼을 때 끌 수 있는 스위치와 중단 기준이 있다
- [ ] 해상도별로 빠지는/달라지는 기능을 정책으로 적었다 (+ 인앱웹뷰·iOS 세션·권한 거부 시 대체 경로)
