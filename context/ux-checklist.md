## A. 시스템 상태 가시성 — 로딩·빈 상태·완료 (시스템·기술 예외)

| 항목 | 기획서에 이렇게 쓴다 (조건 → 동작 → 표시) |
|---|---|
| **로딩 피드백** | 조회·제출이 300ms 초과 → 요청 처리 중 → **스켈레톤/스피너** 노출 (빈 화면 금지) |
| **빈 상태(Empty State)** | 데이터 0건(초기 진입 유저 포함) → 정상 응답 → **안내 문구 + 다음 행동 CTA** ("아직 없어요, 만들어보세요") |
| **에러 복구** | 요청 실패 → 에러 감지 → **에러 메시지 + [재시도] 버튼/도움말 링크** (메시지만 띄우고 끝내지 않음) |
| **완료 확인** | 저장·제출 성공 → 처리 완료 → **성공 토스트/체크 표시** (조용히 끝나면 안 됨) |
| **진행 표시** | 멀티스텝(2단계 이상) → 단계 이동 → **"2/4" 단계 인디케이터** |
| **토스트 수명** | 비중요 알림 → 표시 → **3~5초 후 자동 소멸** (안 사라지는 토스트 금지) |

## B. 중복·오조작 방지 · 가역성 (중복클릭·다중요청·되돌리기)
- **「확인 1회」는 DS `Modal`로 그린다 — 브라우저 native `confirm()`·`alert()`을 쓰지 않는다**(2026-09-03 · 애니멀리그에서 열한 자리 발견 — 보관·공지 삭제·심사·초대 거두기·점수 삭제). native는 ⓐ 문구를 강조할 수 없어 **판단을 바꾸는 숫자(「매긴 3건」)가 평문에 묻히고** ⓑ 버튼 순서·기본 포커스가 브라우저마다 달라 **비가역 조작이 Enter 연타로 넘어가며** ⓒ 대화상자에 서비스 주소가 붙고 ⓓ **자동 QA(Playwright·확장)가 그 자리에서 막힌다.** 「확인 모달을 반사적으로 붙이지 않는다」가 「붙이나」를 정했다면, 이 줄은 「붙인 것을 무엇으로 그리나」다 — 한 제품에 두 종류 확인이 섞이면 더 나쁘니 한 번에 바꾼다.
  - **예외**: ① **`beforeunload`(창 닫기·새로고침)의 경고는 브라우저가 그린다** — 문구도 모양도 바꿀 수 없으므로 이 규칙의 대상이 아니다. ② **떠나기를 가로채는 확인**(링크 클릭·뒤로가기)은 답을 **동기로** 알아야 이동을 막을 수 있어, Modal로 바꾸려면 「막고 → 묻고 → 진행」으로 흐름을 뒤집어야 한다 — 사용자가 버튼을 눌러 시작하는 확인과 같은 묶음으로 세지 않는다(2026-09-03 · 개발 지적).


> **확인 모달을 반사적으로 붙이지 말고, 가역성부터 판정한다.** 모달은 사용자를 *무조건 확인 누르기*로 훈련시켜서 정작 위험한 순간에 방어가 안 된다. **되돌릴 수 있게 만드는 것이 물어보는 것보다 강한 방어다.**

| 액션 성격 | 기본 방어 수단 | 기획서에 이렇게 쓴다 (조건 → 동작 → 표시) |
|---|---|---|
| **되돌릴 수 있음** (숨김·보관·상태변경·soft delete) | **Undo** | 실행 → 즉시 반영 → **"되돌리기" 토스트 5~10초** 노출, 누르면 원복 (모달 없음) |
| **되돌릴 수 없음** (발송·결제·영구삭제·외부 전파) | **확인 모달** | 클릭 → **무엇이 몇 건 사라지는지 모달에 명시** → 확인 후 실행 |
| **비가역 + 대량·과금** | **모달 + 입력 확인** | 클릭 → 대상 건수·금액 표시 + **대상명 타이핑/체크박스** → 실행 |

> **Undo를 고르면 백엔드 선행조건이 생긴다** — soft delete 컬럼, 되돌리기 유효시간, 원복 이력. 스키마라서 **개발 시작 후엔 못 넣는다.** 기능 정의서의 "상태 전이"에 **원복 전이**를 같이 적는다.

| 항목 | 기획서에 이렇게 쓴다 |
|---|---|
| **이중 제출 차단** | 비동기 액션 진행 중 → 버튼 **비활성 + 로딩 상태** → 처리 끝날 때까지 재클릭 불가 |
| **비활성 상태 명시** | 조건 미충족 → 버튼 비활성 → **투명도↓ + 커서 변경**으로 정상과 구분 + **왜 비활성인지** 문구/툴팁 (이유 없는 비활성 = 막다른 화면) |

## C. 폼·입력 (입력 예외: 빈값·최대·중복·경계값)

| 항목 | 기획서에 이렇게 쓴다 |
|---|---|
| **라벨 상시 노출** | 입력 필드 → 항상 → **필드 위/옆에 라벨** (placeholder만으로 라벨 대체 금지) |
| **에러 위치** | 검증 실패 → 해당 필드 → **그 필드 바로 아래 에러** (폼 최상단 일괄 표기 금지) |
| **인라인 검증** | 필드 벗어남(blur) → 즉시 검증 → 문제 있으면 표시 (제출 후에만 검증 X) |
| **필수 표시** | 필수 필드 → 진입 시 → **`*` 또는 (필수) 라벨** |
| **제출 피드백** | 제출 클릭 → 처리 → **로딩 → 성공/실패 상태** 순차 표시 |
| **입력 타입** | 이메일·전화·숫자 → 입력 → **전용 키보드/타입**(모바일 `inputmode`) |

## D. 접근성 — 정책으로 못박을 것

| 항목 | 기획서에 이렇게 쓴다 |
|---|---|
| **색만으로 정보 전달 금지** | 상태 구분(성공/에러 등) → **색 + 아이콘/텍스트 병기** (빨강 테두리만으로 에러 표시 X) — *상태 배지 설계에 직결* |
| **본문 대비** | 본문 텍스트 → **명도 대비 4.5:1 이상** (회색 위 회색 금지) |
| **아이콘 버튼 라벨** | 아이콘만 있는 버튼 → **`aria-label`/대체텍스트** 필수 |
| **폼 라벨·에러 안내** | 입력·에러 → 스크린리더가 읽도록 **라벨 연결 + 에러 알림(role=alert)** |
| **키보드 이동** | 모든 기능 → **키보드로 접근 가능**, 포커스 링 유지 |
| **모바일 본문 크기** | 본문 → 모바일에서 **16px 이상** |
| **비활성 조작의 가시성** | 조작이 **「있는데 지금 못 쓴다」**(끝에 닿았다·조건 미충족)면 **보여야** 한다 — 위치·상태를 말하므로. **「이 줄엔 없다」**(해당 없음)면 사라져도 된다. DS `IconButton weak`은 비활성이면 사라지는 규칙이라(설치 패키지 dist · 우리가 못 고침) 「있는데 못 쓴다」 자리엔 `outline` 등 남는 variant를 고른다 (2026-09-08 FAQ 순서 화살표에서) |

## H. 해상도·플랫폼 — **PM만 답할 수 있는 것만** (나머지는 QA 몫)

> 여기 4줄은 "QA가 못 잡거나, 잡았을 땐 이미 재설계"인 항목이다.
> 터치타겟 44px·가로 스크롤·`100vh` 잘림·네이티브 피커 생김새 차이는 정답이 하나뿐이라 PM 결정이 아니다 → `qa-engineer` / 공통규칙에 맡기고 기획서에 반복해 쓰지 않는다.

| 항목 | 기획서에 이렇게 쓴다 (조건 → 동작 → 표시) |
|---|---|
| **해상도별 무엇을 버리는가** | 화면 요소가 MO(~767)에 다 안 들어감 → **남길 것/접을 것/상세로 뺄 것을 지정** → 예: "목록 8열 중 MO는 이름·상태·마감일 3열 + 나머지는 행 탭 → 상세". "반응형 처리" 한 줄은 미정의 (개발자가 대신 결정하게 됨) |
| **인앱 웹뷰** | 카카오·인스타·네이버 인앱 브라우저로 진입 → 팝업 OAuth·파일 다운로드·새창 차단됨 → **외부 브라우저 열기 안내 or 리다이렉트 방식 로그인**으로 대체 경로 명시 |
| **iOS 세션 만료(ITP)** | Safari가 쿠키/localStorage를 7일 후 삭제 → 자동로그인 정책이 iOS에서만 조기 만료 → **자동로그인 기간 정책이 이걸 견디는 방식인지 명시**(서버 세션/리프레시 토큰 등) |
| **권한 거부 시 대체 경로** | 카메라·알림·위치 권한 거부(또는 데스크톱이라 미지원) → 해당 기능 진입 → **대체 수단 제공**(파일 선택·링크 복사·이메일 알림). 대체 경로 없으면 그건 버그가 아니라 미정의 정책 |

## I. 화면의 주된 행동 · 패턴 일관성 (헤맴 방지)

> A~H가 "빠진 상태를 채우는" 그물이라면, 여기는 **다 있는데도 헤매는** 경우를 잡는다.
> 요소가 전부 정의돼 있어도 무엇부터 할지 안 보이거나, 같은 동작이 화면마다 다르면 사용자는 매번 새로 배운다.

| 항목 | 기획서에 이렇게 쓴다 (조건 → 동작 → 표시) |
|---|---|
| **주된 행동 1개** | 화면 진입 → 이 화면에서 사용자가 **할 일 하나**를 지정 → **Primary 버튼은 화면당 1개**, 나머지는 Secondary/Text. 두 개면 "무엇부터"가 미정의 |
| **막다른 화면 금지** | 어떤 상태에서든(빈 상태·완료·에러·권한 없음·검색 0건) → **다음 한 걸음 제공** → CTA 또는 돌아갈 곳을 명시 |
| **같은 동작 = 같은 패턴** | 같은 성격의 동작(저장·삭제·필터·목록→상세)이 여러 화면에 있음 → **먼저 정의된 화면의 컴포넌트·위치·문구를 나머지가 따른다** → 다르게 갈 거면 **왜 다른지 한 줄**. 이유 없는 차이는 그대로 사용자 학습 비용 |
| **문구 일관** | 같은 대상·같은 결과 → **같은 단어** (`app-terms.md` 기준) → "삭제/제거/취소"가 섞이면 다른 기능으로 읽힌다 |

> **화면 요건서를 페이지 단위 1파일로 쪼개는 구조에서 가장 새기 쉬운 항목이다** — 파일이 갈리면 옆 화면과 대조할 사람이 없다. 새 화면을 쓰기 전에 **같은 동작이 이미 정의된 화면이 있는지 먼저 찾는다.**

- 남긴 것은 전부 **"화면이 어떤 상태에서 무엇을 보여줘야 하는가"** = 기획서에 쓰는 행동·상태 규칙뿐.

### 모달·드롭다운 이동 점검 (2026-09-04 배포 결함에서)
- **모달에서 나가는 모든 이동 뒤 모달이 닫히나** — 인터셉팅/병렬 라우트 모달은 소프트 내비게이션에 남는다. 로그인 링크 하나만 고치면 형제 경로가 남으니 모달이 pathname을 보고 닫히게. 비로그인 컨텍스트(시크릿 창)에서 실제 클릭으로 확인 — 서버 렌더 확인은 이동 뒤 상태를 못 본다.
- **드롭다운 메뉴 항목이 모달을 열면** 메뉴가 먼저 닫혀야 한다 — 열린 채 남으면 바깥 클릭 감지 레이어가 모달 버튼까지 막는다(포인터 인터셉트). 「모달은 뜨는데 버튼이 안 눌린다」가 신호.

### dev 서버 낡음 점검 (2026-09-04 · 하루 네 번 헤맨 자리)
- **화면이 코드와 다르게 보이면 dev 서버가 낡았는지부터 본다.** 스키마(prisma generate)뿐 아니라 **라우트 트리(병렬·인터셉팅 슬롯 추가) · 컨텍스트 프로바이더 · 권한 판정 코드**가 바뀌면 재시작이 필요하다.
- **로그는 시각을 먼저 본다.** 지우지 않고 다시 요청해서 **줄이 늘어나는지**로 「지금 나는 에러」와 「낡은 에러」를 가른다 — 안 늘면 낡은 컴파일 결과다.
- **여러 세션이 한 저장소를 쓰면 남의 빌드가 내 화면을 깬다.** `turbo build`는 dev와 같은 `.next`를 쓴다 — 빌드를 돌리기 전에 다른 세션에 알리고, **빌드 직후의 500은 코드가 아니다**. 발견을 옮길 때 [짐작]/[확인함] 표시를 정본까지 따라 붙인다.
- 「화면이 틀린 것」과 「서버가 낡은 것」을 못 가르면 결함을 지어내거나(오늘 ShareButton) 고친 것을 계속 막힌 것으로 본다(심사위원 진입).

### 「할 수 없다」 문구는 서버가 막는지 확인한다 (2026-09-04)
- **화면이 「할 수 없다」고 말하면 서버가 실제로 막는지 확인한다.** 문구는 화면에, 판정은 서버에 있어 따로 낡는다(오늘 「마감은 늦출 수만 있어요」가 화면에만 있고 서버엔 없었다 — 회귀가 아니라 애초에 없던 것).
- **관문·잠금·권한 문구는 「무엇이 지키는가」를 함께 적는다**(설계서·그림 모두). 막지 않는 문구는 문구를 믿는 사람에게만 규칙이고 해 보는 사람에게는 없는 규칙이다 — 그리고 아무도 신고하지 않는다(되는 것을 문제라고 생각하지 않는다).
- 검토 때 관문·잠금 문구를 세어 각각 서버 판정·테스트가 있는지 짝을 본다(막는 테스트·여는 테스트 짝과 같은 결).

### 못 보는 화면은 같은 코드로 같은 상태를 만들어 본다 (2026-09-04)
- 시드가 없어서 · 계정이 없어서 · 운영 로그인이 안 돼서 못 본 화면은 결함으로 올리지도, 정상으로 넘기지도 말고 **같은 코드로 같은 상태를 만든다** — 빈 DB로 잠깐 띄우기, 조건에 맞는 시드 한 줄 넣기, 그 역할로 로그인하기. 확인 뒤 임시 서버·계정은 지운다.
- 「안 보인다」의 세 원인(코드·시드·계정)을 가르는 방법이 곧 이것이다.

### 필수 표기는 화면과 문서가 같은 기호로 (2026-09-07)
- 폼이 있는 화면 설계서는 요소마다 필수 여부를 `*`로 적고 폼 절 머리에 「필수: …」 한 줄을 둔다. 「(필수)」「(선택)」 괄호 말 대신 화면과 같은 `*`. 필수가 하나뿐이어도 붙인다 — 한 칸에만 표시가 붙으면 나머지가 반대로 읽힌다.
- 검토 때 폼마다 「필수 집합이 문서·화면·서버 검증 셋에서 같은가」를 본다.
